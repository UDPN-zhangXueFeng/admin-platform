# 审批业务侧接入开发文档

> 确认稿 · 2026-10-21  
> 汇总来源：`approval-business-embed-design.md`（2026-10-20）与《Kissen 全网状态字典与维护规范》v1.0（2026-10-20）。来源设计文档标注为已实施；本文整理目标契约与验收口径，不代表已独立核验当前仓库或服务运行状态。

## 1. 目标与范围

统一审批框架与业务页面的状态、查询和详情入口：业务页面能按 `busCode + busId` 查询审批状态并打开共享审批详情；审批操作仍由审批中心统一承载；状态展示遵循全网状态字典。

覆盖的主要消费者：LP 参与对、token 对、资金池、结算单、分成划转，以及审批中心「我发起的」列表。接口提供方负责审批框架改造；消费者按各自前端应用/业务模块接入。本文是跨端契约整理，不指定或改动具体实现文件。

## 2. 统一原则

1. **审批记录是审批状态唯一事实源**：审批状态保存在 `sys_approval_record(+detail)`。业务表 `status` 表示业务生命周期，由策略回调维护；审批在途标记单独展示，不从业务状态推导，也不把审批状态复制进业务表。
2. **审批操作入口唯一**：通过、驳回、撤回、退回均调用 `/v1/mult/approval/*`。业务模块只查询并展示审批，不另建操作端点或复制权限判断。
3. **业务关联键唯一**：按 `(business_code, bus_id)` 关联审批，不依赖业务表 `approval_record_id`。
4. **相同值只在相同列内有唯一语义**：不同业务/不同值域允许同值异义；渲染与筛选必须按字段所属值域处理。
5. **共享详情复用**：业务入口与待办入口进入同一审批详情组件，复用详情、权限与操作逻辑。

## 3. 端到端交互

- **业务列表**：展示业务状态及独立的「审批中」标记；标记可点击进入详情。不在列表行内提供审批操作。
- **业务详情**：展示审批状态区块或「查看审批」入口，不自行渲染审批表单。
- **共享审批详情**：业务页以 `busCode + busId` 调用 `detailByBusiness`；待办列表以 `taskId` 调用现有 `detail`。两种入口使用同一组件；弹窗、抽屉或独立页面是前端呈现选择，不改变接口契约。
- **审批执行**：详情组件调用统一 `process`、`withdraw`、`previousStep` 等审批框架端点，完成后由策略回调使业务生效。

## 4. 后端接口与服务契约

### 4.1 `POST /v1/mult/approval/detailByBusiness`

请求：`{ busCode, busId }`。按业务键解析最新审批记录，并复用既有详情全链路，包括按钮判断、业务内容、流转历史与 `checkBusinessPermission`。

| 业务键查询结果 | 返回与页面行为 |
|---|---|
| 有在途记录（主记录 `reviewer_status` 为 5 或 10） | 返回在途记录详情及当前用户可执行的操作 |
| 无在途记录但有历史 | 返回最新一条已完成记录及历史，供业务页查看上次审批 |
| 没有任何记录 | 返回明确空态；不是 404，也不应作为异常提示 |

前端契约在详情响应中包含 `recordExists`（无记录时为 `false`）与 `taskId`（供详情操作使用）；其余详情结构与现有详情接口一致。最新记录的解析以第 4.4 节在途唯一性约束为前提。

### 4.2 `listBrief`（审批框架 Service，不增加 HTTP 接口）

服务签名支持多业务类型和多业务 ID，以覆盖同一业务列表的多个审批维度：

```java
Map<String, ApprovalBriefDTO> listBrief(List<String> busCodes, List<Long> busIds);
// Map key: busCode + ":" + busId

ApprovalBriefDTO {
    Long taskId;            // record_id
    String applyCode;
    Short reviewerStatus;   // 5/10 在途；3/15/20 终态
    String currentStepName;
    boolean canApprove;
    boolean canWithdraw;
}
```

约束：

- 数据查询必须同时以 `business_code IN (...)` 和 `bus_id IN (...)` 限定；禁止把全量在途业务 ID 拉入内存再匹配。
- `canApprove` 批量复用 `CommonApproveServiceImpl.handleApproveButton` 的权限口径。
- `canWithdraw` 仅在创建人为当前用户且主状态为 5 时为真。
- 业务服务将摘要合并到自己的列表响应，不由前端逐行发审批查询。
- 本次消费者：LP 参与对（KLP、KLS 两个业务码）、token 对、结算单、分成划转。

### 4.3 `POST /v1/mult/approval/applyPage`

提供「我发起的」列表：按 `create_user_id = 当前用户` 查询，可过滤业务类型、状态、关键字，并返回当前节点和撤回权限提示。

前端请求：`{ page, data: { businessCode?, keyword?, reviewerStatus? } }`。列表行字段：`taskId / applyCode / businessCode / busDesc / businessId / reviewerStatus / currentStepName / canWithdraw / createTime`。撤回仍调用既有 `withdraw`。

**已知业务语义**：门户/网关白名单请求不写 `CURRENT_ID`，其审批记录 `create_user_id = 0`，因此不出现在任何人的「我发起的」列表；这些记录也不能由发起人撤回（撤回要求用户 ID 与 `create_user_id` 相同），由运营通过驳回/退回处理。这是既定行为，不作为列表缺陷。

### 4.4 `addApproval` 在途唯一性守卫

在 `addApproval` 入口统一检查同一 `(business_code, bus_id)` 是否已有 `reviewer_status ∈ {5, 10}` 的记录；若存在，拒绝重复发起并返回明确业务错误码。

此约束把每个业务键至多一条在途记录变成框架不变量，也是 `detailByBusiness` 能无歧义选择在途详情的前提。业务自身的状态机守卫（例如 LP 开通状态检查）继续保留，因为其语义是能否发起，而非重复审批检查。数据库唯一约束/在途标志列不属于本次必需方案。

### 4.5 `addApproval` 返回 record ID

返回结构补充 `recordId`（或提供返回记录 ID 的重载），调用方不得再通过查询「最新记录」反向补齐关联。

## 5. 业务关联字段清理

`approval_record_id` 数据库列暂时保留，但语义废弃：新代码不读写；禁止新增此列；审批关联统一按 `(business_code, bus_id)` 查询。按来源设计列出的清理项：

- 删除审批提交后的回填/反查最新记录逻辑和 `.approvalRecordId(0L)` 等无意义赋值。
- 删除响应 VO 中仅用于回显审批记录 ID 的字段；详情关联改用 `detailByBusiness`。
- 删除 `LpPoolSaveReqVO.approvalRecordId` 等未被使用的输入字段。
- 删除 LP 对列表 `pending_split` 子查询、token 对全量 `pendingBusIds` 模式，由 `listBrief` 替代。
- 结算单、分成划转列表通过 `listBrief` 返回在途标记。

来源文档列出的代码行号是 2026-10-19 快照；实施核对时应按符号与调用点确认，不应直接依赖行号。验收要求清除相关代码读写，而不是删除数据库列。

## 6. 前端接入约定

### 6.1 列表字段及交互

| 页面 | 审批字段/语义 | 交互 |
|---|---|---|
| LP 参与对 | `pairApprovalPending`（KLP）；`splitApprovalPending`（KLS），均为布尔值；不再使用 `pendingSplit` 数字或 `approvalRecordId` | 在途行显示「审批中」标记并可查看审批；KLS 在途时「设置分成」禁用，同时可跳转详情 |
| token 对 | `pendingChange` 保留，口径包含状态 5、10 的在途审批 | 标记打开共享详情 |
| 结算单、分成划转 | `approvalPending`；不再使用 `approvalRecordId` | 标记打开共享详情；分成划转的审批 `busId` 是 **orderId**，不是 `transferId` |
| 资金池保存 | 请求中移除 `approvalRecordId` | — |

`status` 与审批标记是并列信息。例如业务状态仍为「已生效」而参数变更审批在途时，应同时显示「已生效」和「审批中」。变更审批不改变业务状态，因此业务状态筛选下拉不需要增加「审批中」选项。

### 6.2 审批中心「我发起的」

新增 Tab/列表展示：申请单号、业务类型、描述、状态、当前节点、申请时间、查看操作。查看复用现有审批详情弹窗；筛选复用业务类型与关键字，新增单据整体状态筛选：`3 已撤回 / 5 待审核 / 10 审核中 / 15 已拒绝 / 20 已通过`。

必须区分同一数字在不同字段中的含义：

- 「我发起的」筛选 `reviewerStatus = 3` 表示审批单已撤回。
- 「已办」筛选结果 `3` 表示审批节点通过、`2` 表示节点拒绝。

不可复用这两个筛选器的选项集合或状态变量。

## 7. 状态字典与下拉筛选

### 7.1 通用状态字典

走通用状态值域的业务状态与审批主单状态统一使用 CommonStatusEnum 字典；未知值显示原始数字兜底。常用值：

| 值 | 中文 | English | 含义/备注 |
|---:|---|---|---|
| 1 | 草稿/保存 | Draft | |
| 3 | 已撤回 | Withdrawn | 审批单撤回后的业务回退态 |
| 5 | 待审核 | Pending Approval | 审批在途，首节点前 |
| 10 | 审核中 | Under Approval | 审批在途，首节点已过 |
| 15 | 已拒绝 | Rejected | 驳回 |
| 20 | 已通过/已生效 | Approved / Enabled | 审批语境用 Approved，业务语境用 Enabled |
| 22 | 审核通过待启用 | Audit Passed (Pending Enable) | 预留 |
| 25 | 已签名 | Signed | 预留 |
| 30 | 提交中/冻结 | Submitting / Frozen | 按实体字典语义使用；token 对为冻结 |
| 35 | 最终确认/已结算 | Settled / Confirmed | 结算单专用语义 |
| 40 | 提交失败 | Submit Failed | 预留 |
| 45 | 已删除 | Deleted | 预留/作废流水 |
| 50 | 已停用 | Disabled | |

### 7.2 每页下拉只取实际值子集

选项值和文案均从通用字典取得；每页仅展示该页实际可能出现的状态，不得把完整字典塞入下拉，避免产生必然查空的选项。

| 页面 | 状态值 |
|---|---|
| LP 参与对 | `[1, 5, 10, 15, 20, 50]` |
| 资金池 | `[5, 15, 20]` |
| token 对 | `[5, 15, 20, 30, 50]` |
| 结算单 | `[5, 10, 15, 20, 35]` |
| LP 入网 | `[1, 5, 10, 15, 20]` |
| 我发起的（单据状态） | `[3, 5, 10, 15, 20]` |
| 银行 | `[1, 2, 5, 10, 15, 20, 50]` |

银行状态已于 2026-10-20 将「已登记」从 10 迁移为 2，驳回回退为 15；银行状态并入通用字典。按来源说明，银行下拉原 `[1, 10, 20]` 应改为上述七值；值 2 与 15 是新增选项，3 不可达，不列入筛选。

### 7.3 不使用通用状态字典的独立值域

以下状态不能借用通用字典的标签/解释，必须按各自域定义展示：

- 分成划转处理状态：`1 处理中 / 2 成功 / 3 失败`。
- 交易状态机：`1/5/10/20/25/30/35/40/50/60/70/80/90`，独立于通用状态。
- 网关实例：`1 已登记 / 10 公钥已推送 / 20 已激活 / 50 已停用`。
- 对账差异、风控、日志等自有处理状态。

审批节点状态也是独立于审批主单状态的值域：`0 无法审核 / 1 待审核 / 2 拒绝 / 3 通过 / 4 无需审核 / 9 退回`（其中 9 是前端约定值，后端无枚举）。

### 7.4 字典维护规则

新增或修改状态前先核对该表、该列的现有语义；若新增通用状态，须先评审，再同步 CommonStatusEnum、本文档对应字典和前端字典。需要迁移存量时，先执行按仓库命名规范保存于 `docs/sql/` 的迁移脚本，再发布代码。实体常量、DDL 注释、状态文档、前端字典须保持一致。

## 8. 实施顺序

1. 在 `addApproval` 加 `(business_code, bus_id)` 在途守卫，并定义明确错误码。
2. 扩展 `addApproval` 返回值，包含 record ID。
3. 实现 `detailByBusiness`、多业务码 `listBrief`、`applyPage` 三个查询投影。
4. 清理 `approval_record_id` 读写与 `pending_split`、`pendingBusIds` 旧查询模式。
5. 接入列表摘要字段、「我发起的」列表、业务页详情入口与共享详情组件。
6. 对照状态字典更新各页状态渲染和筛选选项。

## 9. 验收标准

1. 同一 `(busCode, busId)` 已有 5/10 在途记录时，再次 `addApproval` 明确失败；不同业务码但相同 `busId` 可分别审批。
2. `detailByBusiness` 覆盖在途、仅有历史、无记录三态；无记录返回正常空态而非 404；权限与现有详情一致（`menu_key` 权限及超管放行）。
3. `listBrief` 支持多个 `busCode`；LP 对能分别显示 KLP 与 KLS 在途标记；token 对 `pendingChange` 口径包含 5/10；结算单和分成划转正确展示 `approvalPending`；查询 SQL 同时限制业务码和 `bus_id IN`。
4. 「我发起的」能按当前用户查询记录、状态和当前节点；`create_user_id = 0` 的门户/网关记录不可见，且不可由该入口撤回。
5. `approval_record_id` 不再有代码读写；LP `pending_split` 子查询与 token 对 `pendingBusIds` 全量模式已移除。
6. 待办入口与业务页入口打开同一详情组件；通过、驳回、退回、撤回沿用同一权限及操作行为。
7. 从未发起审批的业务打开详情显示空态；业务状态与审批在途标记并列显示、互不推导。
8. 「已办」节点结果 3（通过）与「我发起的」单据状态 3（撤回）分别筛选到正确记录。
9. 页面筛选项符合第 7.2 节的状态子集；银行状态按迁移后值域显示；独立值域仍按各自字典展示。

## 10. 来源材料需对齐的细节

《Kissen 全网状态字典与维护规范》声明其为前端渲染字典及下拉选项的唯一口径来源。审批设计附录 A 的交易状态对照将值 35/40 都写作「已完成」（35 标注历史区分），而状态字典定义 35 为「已入账/Settled」、40 为「已完成/Completed」。若涉及交易状态标签，以状态字典的定义为准，并在正式实现/验收前同步修正不一致的来源表述。
