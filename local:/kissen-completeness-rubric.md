# Kissen 计划完成度评审 Rubric（共享）

## 目的
评估 `.doc/kissen/plan/` 下每份实施计划文档能否让一个独立开发者「照文档直接编码到 100%」。不是文笔评分，是**可实施性体检**。要挑毛病，不要粉饰。

## 四个维度（每维度独立打分 0~100）
- **D1 可追溯性 (Traceability)**：文档里的每个功能声明/字段/规则，是否都能追溯到设计文档的 FR 编号 / 表结构 / 接口路径。fabricated（凭空捏造）= 重大扣分。
- **D2 可实现性 (Implementability)**：开发者据此能否直接动手——文件路径、组件命名、接口 URL+参数+返回、表字段中英文名、zod 校验规则、create/edit mode 差异、busCode 是否齐备。出现「待定/参考XX/稍后补充/TBD」式空引 = 扣分。
- **D3 覆盖度 (Coverage)**：源设计文档里的所有需求点，是否都在计划中有对应落点（菜单项/页面/模块/实施步骤），无遗漏。
- **D4 内部自洽 (Internal consistency)**：章节齐全无空洞、无前后矛盾、编号/命名一致、与 02 架构契约一致、与 README 消歧一致。

## 完成度分级
- 95~100：生产就绪，开发者可直接据此实施
- 80~94：基本可实施，小缺口可凭合理默认补齐
- 60~79：有阻塞缺口，部分章节需返工
- <60：重大缺口，需重做

## 根因分类（关键——决定能否凭文档自身达到 100%）
- **A 内部可补**：文档自身漏写/不一致/信息不足，补写即可，不依赖外部。
- **B 外部依赖**：缺后端接口契约、缺设计稿、缺产品决策、缺甲方信息——**无论文档写多详细都到不了 100%**，这类必须标为 `needs_user_input`。

## 输出要求
每个缺口必须归因到 A 或 B。B 类缺口写进 `needs_user_input`（给出问题、为何需要、对实施的影响）。不要含糊其辞，不要为了好看给高分。
